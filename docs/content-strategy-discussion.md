# Wuhua 古籍内容管理：现状与路线讨论

日期：2026-09-23  
用途：保留早期路线讨论，**不是版权法律意见**。

> 后续决定：MVP 已采用 Wikisource 主源、固定修订、集中署名、独立解读的简化路线。三本正文已导入；不再以纸本校勘作为门槛。下文的单篇候选、暂停扩量和待选型描述均为当时状态，当前方案见 [README](../README.md)。

## 一、我们在做什么

Wuhua（物化间）是一个现代古籍阅读器，核心体验是读原文、逐层理解、形成自己的认识，而不是建立专业古籍校勘数据库。

当前 MVP 包含《庄子》《道德经》《论语》各六则精选，支持字词解释、今译、思想与上下文解读、概念关联、跨书阅读路径，以及保存在浏览器本地的笔记、收藏和阅读进度。

现在希望解决的问题是：**如何以可持续的成本扩充古籍内容，同时让正文、解释与来源信息不再混在一起。**

## 二、最初采用的方向

最初讨论提出：不要直接把 ctext 等网站当作可批量搬运的素材库，而应建立自己的内容结构，把外部来源作为可以替换的输入。

建议的层级是：

```text
外部来源 → 导入适配 → 作品 → 版本 → 篇章 → 段落 → 句子
                                           │
                                      独立注解与概念
                                           │
                                         阅读器
```

当时考虑的来源包括 Wikisource、Harvard 公版扫描及语料、Kanripo、chinese-poetry 等。但这些来源**尚未完成同口径比较和选型**，此前聊天中的推荐不能视为已经核实的项目决策。

## 三、已经实际完成的工作

### 1. 内容模块化

原本集中在一个文件里的内容已经拆分为：

- 作品、版本、篇章、正文。
- 字词、今译、解读、反思问题等独立编辑内容。
- 概念关系与阅读路径。
- 来源、修订号、许可证据及处理状态。

阅读器通过兼容层读取这些内容，原有选段 ID 保持不变，因此不需要迁移既有笔记、收藏或链接。

目前仍在同一个项目仓库内，**没有拆成独立内容仓库或服务**。每则选段暂作为一个句子单元，并没有完成真正的句界校勘；注解也还是每段一份编辑内容，未实现多注家版本选择。

现有选段的底本与授权状态标为待核验。ctext 链接仍保留为交叉参考，不把链接本身当成获取来源或复用授权证明。

### 2. 一次真实的候选导入

试导入对象是维基文库的《論語／學而第一》，固定修订号为 **2058123**。

成果：

- 保存原始 wikitext，可离线重建。
- 提取 16 则正文。
- 将 5 条异文说明从正文中分离出来。
- 保留原字与标点，不做简繁转换。
- 保存来源、修订、署名、许可说明及修改说明。
- 所有候选引用固定到该修订，而非不断变化的最新页面。

该候选**没有接入正式阅读目录**，没有替换现有选段，也没有自动生成新的现代解读。

### 3. 验证与交付状态

模块化与候选导入分别完成了本地提交。测试及生产构建通过，尚未 push 或部署。

这证明了当前样本可以完成转换、现有阅读器保持兼容；**不证明批量导入已经可行，也不证明完成版权核验或学术校勘**。

## 四、试验暴露了什么问题

### 1. 普通网页提取会污染正文

网页上的异文提示会被一些正文提取工具直接拼进原文。例如“也已”的附读“一作『也已矣』”可能被当作正文的一部分。

本次通过解析原始 wikitext 并单独保存异文解决了这个样本的问题，但这不是一个可直接推广到任意古籍页面的通用方案。

### 2. 当前导入器过于专用

现在的脚本只支持这一固定篇章的结构、章节标记和少量模板，遇到未知结构会报错。这适合做安全、可重复的小实验，不适合按篇复制扩展。

**如果每加一篇都要写解析规则和修补模板，维护成本会随内容增长而迅速上升。** 本次尚未测量其他数据源或大规模样本，因此还不能断言“古籍导入本身都很困难”。

### 3. 权利信息仍未形成明确结论

本次观察到：

- 《论语》作品主页声明作品属于公有领域。
- 章节页面页脚有 CC BY-SA 4.0 的站点文字声明。
- 本次未找到该章节明确对应的纸本版次或扫描底本。

候选材料因此暂按 CC BY-SA 4.0 保守保存和标注，底本为空、版本仍为草稿、人工校勘状态为未完成。

但需要纠正一个容易造成额外负担的推断：

> 站点统一页脚不能单独解决具体古代正文的权利判断；未找到纸本底本，也不自动意味着文本不可使用。

应分别判断古代作品、电子转录、现代标点、注释及数据库组织等具体内容，而不是笼统地把“来源不够清楚”变成逐篇人工校勘的工程要求。

## 五、目前对方法的反思

用户提出的核心质疑是：**如果内容扩充有这么强的不便，就应该评估方法，而不是继续增加流程。**

对此，目前的判断是：

1. **正文与注解分离值得保留。** 它直接服务阅读器扩展，不依赖最终选择哪家来源。
2. **完整校勘体系不应成为 MVP 前提。** 扫描逐页对照、多版本校勘、精细句界等能力应由实际产品需求驱动。
3. **本次只验证了“能导入”，没有验证“值得这样持续导入”。** 不能把一篇专用脚本跑通当作选型成功。
4. **应按整套数据源评估，而不是逐篇解决。** 优先寻找结构统一、覆盖足够、权利边界可解释的来源，再做一次有代表性的转换验证。
5. **不应默认追求 PD／CC0 是唯一解。** 若产品能接受并履行某种开放许可的义务，它可能比从扫描重建更经济；但明确的仓库许可证也不能替代对数据来源的核查。

## 六、真正需要先明确的产品约束

不同用途会改变来源选择，不能把最严格的远期需求全部提前压到 MVP 上：

| 需要确认的用途 | 对选型的影响 |
| --- | --- |
| 提供阅读、学习与独立编辑解读 | 先明确正文能否按计划使用、需要怎样署名和展示许可 |
| 商业化 | 核查许可是否允许对应商业用途；开放许可不等于禁止商业化 |
| 分发完整正文数据、提供下载或内容 API | 需要明确再分发、修改说明和相同方式共享等义务 |
| 将内容任意再授权或作闭源数据资产 | 比单纯展示阅读需要更大的权利自由度 |
| AI 检索、训练或其他再利用 | 应针对具体用途判断，不能从“可阅读”直接推导 |

目前这些远期用途尚未全部确定。尤其需要讨论：**是否确实要求整个正文底库都是 PD／CC0，还是可以接受合适的署名、相同方式共享等条件。**

## 七、可比较的路线

以下是待验证的路线，不是已经得到的结论：

| 路线 | 主要价值 | 主要代价或不确定性 |
| --- | --- | --- |
| 选择一个结构统一、来源可解释的开放数据集 | 可能用一次转换覆盖首批三本书，维护相对集中 | 要核查数据来源、许可适用范围、质量和实际覆盖 |
| 继续以 Wikisource 为主要输入 | 有可追溯修订和可查看的原文页面，本次已验证一个样本 | 需验证页面结构差异是否可控，不能继续一篇一个脚本 |
| 从明确公版的扫描或可靠转录重建 | 能更清楚地掌握具体底本，适合重视版本的产品 | OCR、校对和版本整理投入高，可能偏离阅读 MVP 的重点 |
| 暂时保留精选内容，先验证阅读体验 | 最快推进产品，避免过早建立古籍基础设施 | 内容覆盖有限；已有选段的来源问题仍需处理，不能因数量少而忽略 |

## 八、建议与待讨论问题

当前建议是：**暂停按篇扩量和新增专用解析器，保留模块化成果，先完成小范围数据源选型。** 此建议尚待讨论确认。

选型时关注四项即可：许可及来源、首批三本书的覆盖、结构一致性、持续维护成本。不预先决定要做一个“万能古籍平台”。

希望讨论得到的答案：

1. 我们的核心产品是学习阅读器，还是有明确版本要求的古籍资料库？
2. 是否真的需要纯 PD／CC0，还是可以接受特定开放许可及其义务？
3. 有没有现成、统一且来源可信的数据集，可以避免逐篇解析网页？
4. MVP 是否需要三本全文，还是先用精选内容验证价值？
5. 哪些质量门槛必须现在满足，哪些可以在扩量后再做？

**一句话概括：内容模块化已经落地，但规模化来源路线尚未选定；当前最需要的是确认产品约束并比较数据源，而不是继续把单篇导入做得更复杂。**
